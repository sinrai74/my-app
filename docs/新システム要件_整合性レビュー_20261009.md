# 新システム側への要件（候補）: 現行コード整合性レビュー（2026-10-08）

作成日: 2026-10-09 ／ ステータス: **要件候補の記録（採否は未判断・現行には適用しない）**

根拠: 設計書 Phase0.5 v1.1.8 ⑳20.3「上記以外の変更要求はすべて新システム側（Phase 1以降）への要件として docs/ に積み、現行には適用しない」

本書は、2026-10-08 の現行コード整合性レビューで見つかった事項のうち、現行（Feature Freeze 中）には適用しないものを記録する。R1〜R17 はレビューが挙げた項目、R18〜R23 は `docs/上位判断記録_整合性レビュー対応方針_20261009.md` 判断案4・判断案5で現行に適用しない案とした項目である。判断案4・判断案5は、元のユーザー回答を一次資料で確認できないため、提案・未確認である（同書 §4 A2）。

- 各項目は要件の**候補**であり、新システムの正式な要件として採用したものではない。
- 「事実」のうち、`docs/上位監査記録_整合性レビュー実証_20261009.md`（以下「実証記録」）で確認したものはその旨を付記した。付記のないものはレビューの報告である。
- 「扱い（案）」はレビューの案で、判断は未了。

---

## R1. レースタイプの語彙不一致（BuyScore の race_type 補正が常に無効）

- 事実: `notify_arashi._classify_race_type()` は「イン逃げ型 / 1残り荒れ型 / 大荒れ型 / 混戦型 / 4カド型 / モンスター型」を返す。
  `x_buyscore` の `_race_type_bonus()`・`race_type_points`・`investment_type()` は「本命戦 / 混戦 / 超混戦 / 荒れ戦」をキーにしている。
  hit_record.csv の race_type は「イン逃げ型 128 / 1残り荒れ型 116 / モンスター型 11」。
- 影響: race_type 補正は常に0、最大点数は常に既定4点、`investment_type` の「本命戦→堅実」も不発。
- 扱い（案）: どちらの語彙を正とするか決め、対応表を1か所（設定）で持つ。

## R2. Monte Carlo 確率の計算結果が使われていない

- 事実: `_evaluate_bets()` は `has_exhibition=False`（朝刊AI で常時）のとき `scenario_probs` を作らない。
  ブレンド重みは「`not mc_probs or not scenario_probs` → PL 0.55 / 市場 0.45」となり、
  毎回3,000回計算している `mc_probs` の重みが0になる。コメント「MCシミュレーション自体は展示の有無に関係なく実行すべき（旧実装のバグ修正）」と結果が矛盾。
- 扱い（案）: MC を使うなら重み表を見直す。使わないなら計算を省く。

## R3. 同じ「危険度」でも場補正の有無で値が異なる

- 事実: `calculate_upset_score_v2()`（notify・hit_record の `danger_score_v3`）は `venue` を渡して算出する。
  危険艇速報（`x_ranking._calc_danger_breakdown`・`calc_rank_index_v2`）と `_evaluate_bets()` の
  `calc_rank_probabilities_v2()` は `venue` を渡さない（場補正なし）。後者は `match_index` も0固定
  （6号艇1着の特別条件判定が upset_score のみで決まる）。
- 影響: 「全ブランドで同じ評価基盤」（x_asahi_scoring の設計目的）が成り立っていない。
- 扱い（案）: `build_race_evaluation_v4()` の出力を全経路で共有する。

## R4. MLモデル入力の欠落と学習/推論の前処理差

- 事実: `model_all.pkl` の特徴量は42列。推論側 `_predict_win_prob()` が値を入れているのは
  艇番・全国勝率・モーター2率・平均ST・当地勝率（＋派生）のみで、全国2率・当地2率は存在しない属性
  （`win_rate2` 等）を参照して常に NaN。出走表で取得可能な 年齢・体重・級（`racer_class_number`）・
  全国2率・当地2率・ボート2率、fan の能力指数・コース別複勝率、ナイターフラグも未投入。
- 前処理差: 学習（retrain.py）は欠損を 0 埋め、`_IN順位` は `rank(method="min")`。推論は列中央値埋め
  （全行 NaN の列は NaN のまま）、`rank()` 既定（average）。
- 扱い（案）: 新システムの FeatureBuilder で学習と同一の前処理を共有する。

## R5. ナイター場の集合

- 事実: notify（5か所）・`rebuild/adapters/providers.py`・`config.NIGHT_RACE_VENUES` が
  {4平和島, 6浜名湖, 12住之江, 17宮島, 20若松, 21芦屋, 22福岡, 23唐津, 24大村} を使う。
  一般に知られるナイター開催場（桐生・蒲郡・住之江・丸亀・下関・若松・大村）と一致しない（要確認）。
- 影響: night_factor(-0.08)・ナイターフラグ（学習特徴量）・hit_record の night 列。
- 扱い（案）: 正しい集合を設定ファイル1か所で定義し、学習・推論・記録で共有。

## R6. AI一致指数のランクボーナス境界

- 事実: `x_note_report._calc_match_index()` は 80/60 の固定境界。`rank_of()` の A は 65。
  scoring_spec は「rank_of を単一の基準」と規定。
- 扱い（案）: どちらかに統一（一致指数の値が変わるため凍結期間中は据え置き）。

## R7. 上位進出指数 top2 / top3 が 100 を超える

- 事実: `calc_rank_index_v2()` は top2 = (P1着 + P2着)×100、top3 = (P1+P2+P3)×100。各着順の分布は
  艇間で独立に正規化されているため、和は「2着以内の確率」にならず 100 を超え得る
  （golden4 例: 20260703_04_01 の4号艇 top3 = 124.8）。新聞に「3着以内124.8」と表示される。
- 扱い（案）: 着順確率を同時分布（Plackett-Luce 等）から導出する。

## R8. BuyScore の market_gap のスケール

- 事実: notify は `market_gap = 順位差/5`（-1〜1）を渡すが、`calc_buyscore()` は `abs(market_gap)/3.0` で正規化
  （最大でも 0.33）。さらに `abs()` のため「市場の方がモデルより高評価」も加点になる。
- 扱い（案）: 単位と符号の定義を揃える。

## R9. 資金管理の連敗停止が自己解除しない

- 事実: 連敗判定は notify `_get_bet_multiplier()` と `x_buyscore.get_bet_multiplier_extended()` の2実装。
  どちらも hit_record の直近行から連敗数を数える。共有 hit_record.csv（07-04 まで）では
  全行で 20 連敗、購入行のみで 13 連敗 → いずれも停止(>=10)。停止中は購入行が増えないため、
  購入行のみで数える設計では停止が永久に解除されない。現行は見送り行（purchased=0）も数えるため、
  見送り予想の「仮想的中」でのみ解除され得る（意図した仕様かは不明）。
- 扱い（案）: 解除条件（日付リセット、仮想成績での判定等）を明文化し、実装を1つにする。

## R10. 成績集計の母数の定義

- 事実: `x_verification.aggregate()` の通知件数・的中率・連勝連敗は `pred_combo` がある行すべて
  （見送り 145行を含む）。`x_results_common.calc_overall_roi()` は購入行のみ。
- 扱い（案）: 「予想の的中率」と「購入の的中率」を分けて定義する。

## R11. ranking_filter.json が notify ジョブに届かない

- 事実: `x_ranking.py` が出力する `ranking_filter.json` は x_ranking.yml でコミットされず、
  別ジョブの notify_arashi.yml からは参照できない。`_is_ranking_target()` は常に True（全許可）。
- 扱い（案）: フィルタを使うなら受け渡し経路を決める。使わないなら削除。

## R12. 運用データの永続化方針の二重化

- 事実: README・.gitignore・ops_check は「運用データは Git 管理外（Releases で永続化）」。
  実運用の x_ranking.yml は motor_history.csv・ranking_cache.json・daily_stats.json 等を git commit で永続化。
  さらに `x_results_common.load_daily_stats()` は Release の daily_stats.json を先に取得して手元を上書きする
  （Release に古いアセットがあると、コミット済みの新しい版より古い版で集計される）。
  補足（実証記録）: x_ranking.yml の実績ページ生成ステップには GITHUB_TOKEN がないため、そのステップでは Release からの取得は行われない。notify 実行時の `motor_history.csv`（場別統計）では Release の古い版が使われる。
- 扱い（案）: 永続化先を Releases（data-store-v2）に一本化する（設計書 1.1.7 の命名規約に従う）。

## R13. 転がし（x_korogashi.py）と朝刊AIポリシー

- 事実: `_apply_preview_to_boats()` で展示・気象を採点に使う。`scan_all_races()` の `odds_map` は常に空で、
  EV は「想定オッズ × 1/想定オッズ」により恒等的に 1.0（5・6号艇の EV>=1.6 条件は成立しない）。
  `_phase_header()` は dataclass に対して `.get()` を既定値評価で呼ぶため、呼ばれれば AttributeError（現状未使用）。
- 扱い（案）: 転がしをポリシーの例外とするか判断し、EV 計算を実オッズに基づくものにする。

## R14. 万舟警報「荒れる理由」の1コースST比較

- 事実: `_upset_reasons()`・`_pick_key_racer()` は全艇の「1コースST実績」を比較し、
  「5号艇が1コースST実績0.11で最速」のような文を出す（5号艇は通常1コースに入らない）。
  新聞の危険艇カードは「担当コースST」に一本化済み（⑥）で、表示方針が不一致。
- 扱い（案）: 担当（進入予定）コースの ST で比較する。注目選手の選定結果も変わるため評価変更扱い。

## R15. config.py の場コード 02/03

- 事実: `config.COURSE_DIFF` は "02"=江戸川・"03"=戸田。公式（`notify_arashi.VENUE_NAMES`）は 02=戸田・03=江戸川。
  `parsers.parse_k_file` の場名、`features.get_venue_config` の場別補正（旧パイプライン main.py 系）に影響。
- 要確認: 各ブロックの設定値が「場名」を想定したものか「コード」を想定したものか。

## R16. 表示テキストの古い記述

- `x_note_report.BRAND_CRITERIA` の掲載条件が「展示・ST・…・気象」等、朝刊AIで使っていない指標を含む。
- 新聞フッター「AI Engine v3.0」、`x_brand_config.AI_VERSION = "v3.1"`、評価エンジン `asahi-v4.0-unified-engine` が不一致。
- `asahi_config.json` の `_comment` が「v1.0」のまま、`danger_score.thresholds` は Ver4 で未使用。

## R17. その他

- `update_fan_files()` は毎月1日に `fanYYMM.txt` を取得しようとするが、fan ファイルは年2回（4月・10月）発行のため
  他の月は失敗する。また `git push https://{token}@github.com/...` を os.system で実行している。
- `run()` は通知停止中でも GMAIL_ADDRESS / GMAIL_APP_PASS が無いと終了する。
- `__pycache__/*.pyc` がコミットされている（.gitignore 対象）。
- `hit_record.csv`（共有版）に同一レースの重複2件（2026-07-02 芦屋6R・蒲郡6R、cost が異なる）と
  結果「不明」1件（2026-07-01 若松11R）がある → データ復旧手順（⑥）で扱う。

## R18. 出走表の級別が取得できていない（パッチ0001・B2）

- 事実（実証記録で確認）: 級別を `racer_class` / `racer_grade` から取得しているが、programs API v2 にこのキーはなく、級別は `racer_class_number`（1=A1, 2=A2, 3=B1, 4=B2）にある。現行の級別は常に空欄。2026-01-01 のデータにもキーはなく、API仕様変更ではない。
- 影響: 1号艇A1の強制スキップ、A2の減点、class_risk、class_gap_effect、危険度の級別評価、新聞・CSV の級別表示が働いていない。2026-10-08 の試算では、修正すると閾値を超えるレースが 103→75 になる。
- 扱い（案）: 新システムの Provider で `racer_class_number` を級別に変換する。Rebuild の `adapters/providers.py` は現行の `_extract_boats_from_program` を呼んでいるため、Rebuild 側での取得経路も合わせて決める。golden4 の入力は級別空欄を前提に固定されている。

## R19. 実績ページの払戻合計（パッチ0004・B4）

- 事実（実証記録で確認）: `x_results_common.calc_overall_roi()` は的中行の `payout`（100円あたりの払戻）をそのまま払戻額として合計しており、1点100円を超える購入では過小になる（共有版 hit_record で 3,400円 に対し実額 10,200円）。
- 扱い（案）: 払戻額を `cost + profit`（または購入額×payout/100）で求める。

## R20. 分析CLI・ログ系の不具合（パッチ0005・A1）

- 事実（実証記録で確認）: `_run_calibration_check()` の未定義変数 `hits`、ROI の計算、`hit="-1"` の扱い。`_check_losing_streak()` が存在しない列 `notified_combo` を参照。`--stats` が1行100円を仮定。`send_preview_notification()` 末尾に到達はするが何もしないコード（未定義変数による NameError を握りつぶす）。
- 扱い（案）: 新システムの検証・ログ機能で cost/profit に基づく集計を実装する。

## R21. ランク表示の境界の不一致（パッチ0007・B6）

- 事実: 新聞は `x_brand_config.rank_of()`（S80/A65/B50/C）、X投稿・メール本文・CSV は S80/A60/B の3段階。
- 扱い（案）: 表示ランクを `rank_of()` に統一する（R6 と合わせて判断）。

## R22. 新聞メールの X投稿候補の選び方（パッチ0008・B7）

- 事実（実証記録で確認）: `send_note_report()` は会場名の文字コード順で先頭のレースを「最注目」としている。2026-10-08 のデータでは びわこ8R（一致指数51.4）が選ばれ、一致指数1位は江戸川6R（52.7）。
- 扱い（案）: AI一致指数が最大のレースを選ぶ。

## R23. motor_history の着順コード 7〜16 の扱い（パッチ0006の一部）

- 事実（実証記録で確認）: `place` 列に 7〜16 が 1,214 行ある。`calc_awakening()` はこれを平均着順にそのまま含める。`calc_hot_motor()` の着順スコアは0点扱い。
- 扱い（案）: コードの意味（失格・欠場等）を確認したうえで、平均着順・2連率の計算での扱いを定める。

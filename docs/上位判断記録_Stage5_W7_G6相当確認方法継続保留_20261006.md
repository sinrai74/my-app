## 3. 既存資料間の不一致

G6 の確認方法について、Step5-0 は「ログで確認」とし（F2）、Step6-0 は「NullNotifier強制＋ShadowRunnerのRuntimeError二重防止で担保」としている（F3）。両者の関係を整理した記録はない。継続基準書 §9 は Step6-0 由来の定義を踏襲するとする一方、§11 は G6 を「未実測」とし、実測開始の要否を判断しないとしている（F4）。

W7 は「G6相当」であるため、W7 の確認方法を定めることは、Go/No-Go 条件である G6 の確認方法を定めることに及ぶおそれがある。

## 4. 判断内容

### 判断1：W7

W7（Stage 5 の実測行「実送信0件（Shadow中）の確認（G6相当）」の確認方法）は、既存資料の間で確認方法が一致していないため、**引き続き保留する**。

### 判断2：本判断の意味

1. G6 の定義そのものは変更しない。
2. Step5-0 の「ログで確認」と、Step6-0 の「NullNotifier強制＋ShadowRunnerのRuntimeError二重防止で担保」の関係を解消しない。両者の不一致は未確定のまま残す。
3. 継続基準書 §11 の「既存資料にない推論では判断しない」を維持する。
4. `shadow_real_sends` を計測値へ変更する判断をしない。
5. W7 の継続保留は、G6 の未達の判定ではない。G6 の達成の判定でもない。
6. 固定値 0（F6）を、実送信0件の確認として扱わない。実測がないこと（F9）のみを理由として、G6 を未達とも扱わない。

### 判断3：維持する既存の制約

次の既存の制約は、変更せず維持する。

- Shadow 期間中の Rebuild からの実送信禁止
- NullNotifier の強制
- ShadowRunner の送信前・送信後の二重防止

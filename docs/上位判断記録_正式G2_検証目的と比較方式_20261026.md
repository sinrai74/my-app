## §3 判断2：比較元と Shadow での取得方式

### 3.1 判断内容

- 正式G2の比較元は、Shadow で凍結版の v4 関数を変更せずに呼び出して得る dict とする。Legacy のコード（`notify_arashi.py` を含む）は変更しない。
- Step6-1 との関係：
  - Step6-1 の既存の記述・基準（Shadow の Legacy側を sent とすること、および継続基準書 §8.5 が記載する再実行の回避）は変更しない。本書は Step6-1 の方針を全面的に解除するものではない。
  - 正式G2の比較に限り、比較専用の v4 呼び出しを行う方針は、2026-10-26 の上位判断で承認された。
  - Step6-1 の原文は本書の作成時に確認していない。本書は Step6-1 の意味を、継続基準書 §8.5 の記載を超えて解釈しない。
  - この比較専用呼び出しの具体的な呼び出し位置、実行条件、安全性（Legacy・本番経路への影響が無いことの確認を含む）は未決定であり、正式カウント開始前に定める（§6）。
- 比較専用の値は、本番の保存・表示・配信経路に流さない。監査に必要な実行条件・判定証拠の保持は、これとは区別する。
- Evaluate Once との関係：
  - Shadow における比較専用の呼び出しに限って Evaluate Once の例外とする方針は、2026-10-26 の上位判断で承認された範囲に含まれる。
  - Rebuild の通常評価は1レース1回とする。

  - 具体的な実行方式は §6 の未決定事項とする。

### 3.2 入力条件

- 「同じ条件の入力」は、艇データだけの一致を意味しない。艇データ、会場統計（`x_venue_stats`）、fan ファイル、`asahi_config.json` 等の設定、その他評価結果に影響する外部データ・実行条件について、両側で同一条件を確保する方法と、その同一性を確認する方法を、正式カウント開始前に定める（§6）。
- 方式の候補として、同じプロセス内で同じ艇データ・設定オブジェクト・会場統計キャッシュを両側に渡し、実行前後の不変性をハッシュ等で確認する方法（B' 検証のハーネスで用いた方法）を検討対象とする。本書はこれを採用しない。
- B' 検証は隔離環境で行われ、会場統計を git の `motor_history.csv` から読んだ。本番 Shadow（GitHub Actions）が実際に使う取得経路は未確定である（§7）。

## §4 判断3：本番切り替えとの関係

- 正式G2の合格は、本番出力の再現、本番切り替えの安全性、G3の完了を意味しない。
- 本番切り替え前に、少なくとも次を別途判断し、本番切り替えの前提条件とする。
  1. 評価値の変化の受け入れ：本番の評価が v2＋ML加点から v4 に変わることを受け入れるか。
  2. 級別分岐の検証：級別が空の状態の比較では、A1・A2・class_gap、危険度・rank_index の級別項目は検証されない。この範囲を別途検証する。
  3. G3の状態：G3の検証状態と、本番切り替えに必要な合格条件。

## §5 正式カウントの対象

- 正式カウントは、2026-10-26の上位判断に基づき、§6の事項を確定した後、その確定条件に従って実行した結果だけを対象とする。
- B' 168件、Golden 100件、本書以前の Shadow の結果は、正式カウントに含めない。
- §6 の事項が定まるまで、正式カウントは開始しない。

## §6 正式カウント開始前に定める事項（本書では未決定）

1. 差分ゼロの定義と比較対象。
2. 評価時刻など比較の意味に影響する項目を、差分判定の対象に含めるか除外するか（入力をそろえる方法とは分離し、差分ゼロの定義の中で決める）。
3. 比較単位、期間、判定値。
4. skip・broken・実行失敗・比較不能の扱い。
5. 入力差、欠損、取得不能、バージョン不一致が生じた場合の判定とカウント上の扱い（4 と一体で定める）。
6. 実行条件・比較結果・判定根拠など、監査に必要な証拠の保持方法。
7. 基準を変更した場合のカウントの扱い。
8. Shadow比較専用の追加呼び出しと、Rebuild の通常評価1レース1回を両立させる実行方式。比較専用呼び出しの具体的な呼び出し位置、実行条件、安全性の確認方法を含む。
9. 比較対象の入力を同一条件にそろえたことを確認する方法。

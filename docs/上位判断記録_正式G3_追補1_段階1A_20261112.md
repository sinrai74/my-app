## 1. 同一性の条件（第3版 §6 の置き換え）

1. 加点の関数に渡した upset_score が、RaceEvaluation.upset_score（加点前）と同一。
3. 加点の関数の出力（score_post・target_post）が、PredictionContext の upset_score・target_lanes と同一。
5. 加点の関数に渡した win_probs と PredictionContext.ml_probs が、RaceEvaluation.win_probs と同一。
6. 写し取った context の upset_score・match_index・has_exhibition・match_index_approx が、入力つきの評価で使う値と一致。
7. 写し取りの状態が captured で、写し取った候補の中に pred_combo がちょうど1件。
8. win_probs が空または None のときは「予想なし」として別に記録する（カウントの扱いは第3版 §12 の6 と一緒に決める）。

- 条件1・3・5・6・7 のどれかが食い違えば入力不備とする。
- 方式（(b-2) ハイブリッド方式）は変わらない。

## 2. 既知の差異（⑯ の対象外として、ここに記録する）

1. 設計固定書 §5.2 は `BuyEngine.decide(evaluation, prediction, config, bankroll) -> BuyDecision`。現行は `assess(evaluation, prediction, config) -> BuyAssessment`。
2. §3.4 で match_index は RaceEvaluation の評価結果とされるが、G3 の入力つきの評価は、加点後の upset から導いた match_index を使う。
3. B 案では、入力つきの評価を新しいファイルの関数として置き、既存の assess の処理の順序を書き直す。本番切替の前に、既存の assess との一本化を判断する。
4. P2+ は G3 には十分だが最終形とは限らない。Legacy が保存・通知に使う upset_score は加点後であり、本番切替の前に、加点後の値を RaceEvaluation に持つかを再判断する。

- 加点の有無（applied・bonus）は、G3 の記録に毎回残す（設計固定書の「再現性の保証」への対応）。

## 3. 未解決2点の扱い

1. **Prediction と buyscore 最高の候補のずれ**：Prediction の候補（pred_combo）を比較の正本とし、Legacy の基準値も同じ候補から取る。buyscore 最高の候補と食い違うレースは毎回検出し、比較不成立とする。
2. **target の一致**：G3 の判定条件に入れない（条件3 で加点後の値の受け渡しだけを確かめる）。診断 (a) で Rebuild と Legacy の target の両方を記録して一致率を確かめ、出力一致（G5）の前に再判断する。

## 4. B 案の同値性の合格条件（承認済み）

- (a) 入力の追加なしのとき、新しい関数と既存の `DefaultBuyEngine.assess` の6項目（buyscore・investment_type・kelly_fraction・skip_reason・config_version・eval_id）が完全に一致（浮動小数点は ==）。
- (b) 例外の型と、例外が出る条件が一致。
- (c) 固定の乱数の種で1万件のランダム入力（境界の近くを含む）について、(a)・(b) が成り立つ。
- (d) 入力の追加ありのとき、同じ候補・context を x_buyscore の純関数に直接渡した結果と4項目が完全に一致。
- 追加の必須テスト：has_exhibition=False の補正、market_gap（正・負・0）、match_index_approx の True/False と40の前後、composite の有無、「展示なし+信頼度不足」、uncertainty 0.75・disagreement 0.80・buyscore 60 の前後。
- 不合格なら B を使わず停止し、原因を本人に報告する（新しい関数の修正か A への切替かは、そのとき本人が判断する）。

## 3. 設計

### 3.1 仕組み
- sys.setprofile による観測（差し替えなし）。対象は「x_buyscore.py の apply_buyscore」を、ファイルの正規化パス・関数名・最初の行番号（co_firstlineno）の組で識別する。
- 'call' の事象で、frame.f_locals から candidates と context を**深い複製**で取り出す（C4 のため）。
- 'return' の事象で、(1) 戻り値の辞書（passthrough_reason・"buy" の中身）と、(2) その場で書き換え・並べ替えられた引数の候補のリスト（f_locals の candidates）を、深い複製で写し取る。Legacy の比較基準値（buyscore・kelly・passthrough_reason）は、ここから取る。
- 比較基準値をどの候補から取るか（buyscore 最高の候補か、Prediction と同じ pred_combo の候補か）は未決定（03 §9 の U-a）。両方を記録する。
- uncertainty・disagreement・composite は `_evaluate_bets` の戻り値の辞書にもある（notify_arashi.py 2563・2677・2678行目）。写し取りの値と戻り値の値の一致も確かめる（setprofile でしか得られないのは market_gap だけ）。
- 1回の `_evaluate_bets` の呼び出しにつき、call が1回であることを確かめる（2回以上なら捕捉失敗）。

### 3.2 正式G2 の監視との関係
- 正式G2 の評価（formal_g2）とは**別の入口**で使う。G2 の評価の流れ・禁止区分（C7）は変えない。
- G3 の入口では、プロファイラを1つにまとめる。回数の記録（instrument の機能）と写し取りを、同じ観測関数で行う設計とする。instrument.py を変えるか、G3 用の別モジュールにするかは、段階2-1 で決める（未決定）。

### 3.3 失敗の扱い
- 観測関数の中の例外は、すべて受け止める（Legacy の処理に伝えない）。
- 状態の区分（1レースごと）
  - captured：call と return の両方を写し取れた
  - not_called：apply_buyscore が呼ばれなかった（候補0件。C5）
  - legacy_exception：call は写し取ったが、return が無く例外で抜けた（C5）
  - capture_failed：観測関数の中の例外、call が2回以上、複製の失敗、対象の識別の失敗
- 推測の値や既定値では埋めない。

### 3.4 記録する項目
- eval_id、run_id、実行時刻、状態の区分
- 写し取った candidates（全件。呼び出し時と return 時の両方）と context（7キー）、それぞれの SHA-256
- Legacy の比較基準値（buyscore 最高の候補と、pred_combo の候補の、combo・buyscore・kelly。戻り値の passthrough_reason）
- `_evaluate_bets` と apply_buyscore の呼び出し回数
- 観測関数の中の例外の種類（値は記録しない）

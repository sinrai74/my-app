## 1. 歴史的事実と今回の新規採用基準の区別（最重要）

本文書全体を通じて、以下の2種類の情報を明確に分離する。

- **[A. Historical / Confirmed]**：既存資料・既存コードから確認された事実
  （例：Step6-3の完了条件は既存資料から確認不能だった、G1〜G8はStep6-0
  由来、K1はStep6-2c-9由来 等）
- **[B. Newly Adopted Working Definition]**：今回の再設計プロジェクトで
  新たに定義した、今後の完成に向けた作業基準（例：本文書のC1〜C10、
  W案のデータフロー、G3-A/B/Cの再構成 等）

**[B]は過去資料に存在した正式な完成条件ではない。** 過去のStep6-3調査

終了・次工程条件は、既存資料からは確認不能であることが確定している
（出典：`Step6-3_次工程・未完了作業・移行条件の明示有無_確認結果.md`ほか）。
本文書のC1〜C10・Stage定義は、その確認不能な状態を受けて**今回新たに
提案・採用した基準**であり、過去に発見された「本来の正式完成条件」では

## 8.5 evaluation段（upset_score / race_type）のGo/No-Go上の扱い [B・承認済み]

**方針（ユーザー承認済み）**: evaluation段（upset_score / race_type）は
Shadowで**観測・比較・diff記録を継続する**が、**Go/No-Goの100連続一致
（streak）の必須判定対象からは外す**。「観測は残す／Go-No-Go判定には
使わない」。

**根拠**:
- Shadow比較のLegacy側は A = sent保存値（過去実行時の値、Step6-1で正式
  決定されたsent取得方式）、Rebuild側は C = 現在CI実行時の再計算値。
  B = 現在CI実行時のLegacy再計算値は取得しておらず、取得を要求する正式
  設計も存在しない（Step6-1はLegツールへのフック・再実行を明示的に回避）。
- したがって A≠C だけでは「Legacy実装差」か「入力時点差」かを切り分け
  られない。根拠なくLegツール/Rebuildの修正を始めるのは Feature Freeze・

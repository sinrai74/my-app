## 3. 判断（ユーザー判断、2026-10-12）

| # | 判断 | 内容 |
|---|---|---|
| J1-a | オッズ解析障害を ⑳20.3 の「稼働継続に必須の障害修正」に分類する | 必須とする理由は、ML の読み込みを復旧して現行システムの稼働を続けるには、正しいオッズが前提となること（F4・F5）。誤った割り当てを ⑳20.3 の「など」に含まれるものとして扱う。Rebuild の利用経路（F6）は分類の根拠としない |

### 3.1 現在の影響についての記載

今の Legacy 本番は ML の読み込みに失敗しているため（F3）、確認できた範囲では、本障害が Legacy の出力に与える影響は限られている。本分類は、現在の影響の大きさではなく、F4・F5 を根拠とする。

## 4. 同日に承認された修正方針（ユーザー判断、2026-10-12）

| # | 方針 |
|---|---|
| P1 | 組番は HTML のラベル（thead の1着艇番、2着・3着の艇番のセル）から取得する方式を第一選択とする。ラベルを安定して取得できない場合は、位置に依存する方式へ自動で切り替えず、調査して報告する |
| P2 | 欠場艇を含む組番は、既存の戻り値の契約どおり、**キーを入れない**（呼び出し側は `odds_map.get(combo, 0)` で読み、0 以下を除外している：`notify_arashi.py` L2505–2507 ほか） |
| P3 | 取得失敗と解析失敗は、戻り値の契約（`dict[str, float]`、失敗時は `{}`）を変えず、WARNING ログで区別する |
| P4 | 構造を再現した合成 HTML によるテストをリポジトリに追加する。実際のページの HTML はリポジトリに追加せず、手元での検証だけに使う |
| P5 | ⑳20.3 のゴールデンの条件は免除しない。変更前のゴールデンを保持し、変更後のスナップショットを別に生成して比較し、差分と理由を記録する。必要な承認記録が得られるまで、差分を承認済みとして扱わない |
| P6 | 修正は2段階で行う。第1段階は本書・J1-b の記録・追補の作成、第2段階はコード修正・テスト・検証とし、第2段階は第1段階の記録の保存後に開始する |

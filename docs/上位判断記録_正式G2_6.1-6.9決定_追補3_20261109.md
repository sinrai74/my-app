### 2.2 実行ごとの許可（本人判断項目4）【本人：方式】【GPT判断：照合の条件】
- 許可ファイルの置き場所：`g2_permissions/<permission_id>.json`。形式は schema_version 1 で、項目は次のとおり。
  - permission_id
  - race_date（YYYYMMDD）
  - window_start・window_end（UTC の Z）
  - workflow：`.github/workflows/formal_g2_evaluate.yml`
  - ref：`refs/heads/main`
  - mode：formal
  - approved_on（YYYY-MM-DD）
  - approved_by：sinrai74
  - approval_method：github_web_ui
- 照合の条件1〜12（どれも満たすときだけ許可）
  1. ファイルがある
  2. ファイル名と permission_id が一致する
  3. 形式が正しい（重複したキーは拒否）
  4. 履歴で、そのファイルに触れた commit が1件だけで、追加である（改名・削除・再追加は不合格）
  5. 追加の後に変更が無い。集約は main から行う
  6. author が sinrai74
  7. committer が web-flow
  8. 署名の verified が true
  9. commit の時刻が実行の開始より前（タイムゾーンを解釈して比べる）
  10. 許可の commit が実行の HEAD に含まれる
  11. blob が一致する
  12. race_date・時間の窓・workflow・ref・mode が実行と一致する
- 取得の失敗は、どれも許可が無いものとする（fail-closed）。
- 取得の範囲：API の path 指定の履歴は、git の履歴の簡略化に従う。per_page は100。commit の変更ファイル数が 1〜299 のときだけ合格とする（U4・U11）。取得の範囲の限界は証拠に記録する。
- U1：許可1件で認める正式な実行は1回だけとする。許可の条件を満たした最初の実行（開始時刻の順）だけを許可する。
- U7：U1 を保証するのは、集約に入力した run_ids の範囲だけである。その範囲を結果に記録する。
- Y1：同じ許可の2回目以降は手続き違反として記録する。それだけを理由に判定全体を止めず、照合の失敗（終了コード3）にもしない。順序が分からなければ保留する。
- U2・U6：許可の違反が到達の前か後かは、実行の開始時刻で決める。到達の後なら、到達・連続件数を止めず、取り消さない。到達の前、または順序が不明なら、判定を止める（`halted_permission_violation`）。
- 残りのリスク：sinrai74 のトークンで API から作った commit は、本人がブラウザで作った commit と同じ形になる。暗号による本人の証明ではない。Claude が許可ファイルを作らない、という運用の規則に依存する。

### 2.7 d5（正本の保存）【GPT判断。保存場所の正式な仕様は本書の保存をもって確定（Z2）】
- 置き場所
  - 評価の実行の正本：`g2_evidence/<permission_id>/<run_id>-<attempt>/`（07f d5 のとおり）
  - 集約の記録・状態・イベント：`g2_evidence/_aggregate/`
  - 許可 ID の無い実行：`g2_evidence/_aggregate/unattached/` に隔離する。隔離した実行は、許可・集約・達成の根拠にしない。
- 評価の実行の正本には、どの集約から作っても同じになるものだけを入れる。実行区分・照合の結果・基準・取得の時刻は、集約の正本に記録する。
- 保存は作業ツリーへの書き込みだけで、commit は本人の個別の許可による（07f d5 の留保のとおり）。
  - 上書きはしない。同じ内容なら同一の保存、違う内容なら衝突として何も書かない。
  - 追記だけのファイルは、先頭が一致するときだけ追記する。
  - 読み戻して SHA-256 を確かめる。
- 前回の正本は必須とする（Y6）。前回の正本は、集約の順番の記録の最後の行と一致しなければならない。最初の状態（genesis）は、何も無いときだけ使える。確かめられなければ、判定全体を保留する。
- H1・H2 は、追記だけのイベントの記録から求める。自動では解かない。
- 履歴の確かめ（Z3）：集約の workflow は、checkout で全履歴を取る（fetch-depth: 0）。そして、追記だけのファイルが commit のたびに伸びるだけであること、ほかの正本のファイルが追加の後に変わっていないことを、手元の git で確かめる。アプリケーションの追記の制御・集約時の検証・履歴の確かめ・本人の commit の確認を重ねるが、これで改ざんを完全に防げるとは書かない。
- 達成の記録の順（Z4）
  1. 束を commit する
  2. その commit を入力にして、もう一度集約する
  3. 正本・履歴・H1/H2・100件の条件と、集約の終了コード0を確かめる（`ready_for_human_record`）
  4. 本人が達成を記録する
  - 集約のプログラムは、達成済みとは書かない。

### 2.8 H1・H2 の解除【GPT判断】
- H1 と H2 は、別々の追記だけの記録とする。
- H1 の訂正の値は、07f P4 12 の「0（zero）」と「維持（maintain）」に限る。P4-C 相当のイベントには「維持」を使えない。「0」は計算し直しに当てはめる（P4 13）。元の記録は書き換えない。
- H2 の解除は「終了（closed）」に限る。H1 を解除しても H2 は解けない。
- 有効と認めない場合：承認が無い、対象の ID が無い、対象が一致しない、根拠のファイルが無い、根拠の SHA が違う、形式が不正、解除が重複している、解除が矛盾している。
- Z1：解除の承認は、項目4 と同じく、本人がブラウザで commit し、workflow が API で履歴（author・committer・署名・commit の日時・blob・実行の HEAD との関係）を確かめる方式とする。確かめられなければ解除しない。暗号による本人の証明ではないことは、残りのリスクとして記録する。
- Z5：同じイベントを読み直しても、二重には登録しない。解除の後に出た新しい疑義は、新しいイベントとして登録し、再び保留にする。過去の解除の記録は変えない・消さない。

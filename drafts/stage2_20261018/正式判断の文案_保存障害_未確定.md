## 0. 共通の定義（§1〜§2 のすべてでこの定義を使う）

**許可 asset**（Release `data-store` 上で、現行システムが作成・更新・削除してよい asset）

| 本体 | バックアップ |
|---|---|
| `buyscore_log.jsonl` | `buyscore_log.jsonl.bak` |
| `hit_record.csv` | `hit_record.csv.bak` |
| `sent_YYYYMMDD.txt`（YYYYMMDD は8桁の数字。正規表現 `^sent_\d{8}\.txt$`） | 同名＋`.bak` |

- 根拠：保存する側は `x_release_storage.merge_kind`（L274〜）がこの3種を追記型として扱い、`x_state_sync.save` は `sent_[0-9]*.txt` のうち `merge_kind` が認めるもの（＝上の正規表現）だけを保存する。
- 1回の保存で行う操作は、許可 asset に対する GET・POST・DELETE だけ（名前の変更＝PATCH は使わない）。DELETE の対象は、保存対象と同じ名前の本体・`.bak`、および同じ名前で state が uploaded 以外の asset（失敗したアップロードの残骸）に限る。
- 上記以外の asset（`daily_stats.json`、`motor_history.csv`、`local_course_stats.csv`、`hit_record_legacy*` など）は、作成・更新・削除しない。

現行：「notify のログに `[hit_record] N件追記` が出る、または Release の `hit_record.csv` が作られる・更新される」

案：hit_record の正常な生成・更新そのものは停止条件にしない。次のいずれかが確認されたら停止する。確認は、Release の `hit_record.csv` と `hit_record.csv.bak`（＝その1つ前の版）、および notify の実行ログで行う。

| # | 区分 | 条件 |
|---|---|---|
| S1-a | 構造の異常 | `hit_record.csv` が UTF-8 の CSV として読めない、ヘッダが notify の fieldnames（L5149〜、44列）と名前・順序が一致しない、またはヘッダと列数の違う行がある |

## 2. 記録C（上位判断記録_D1見直し_B1再開_20261013）§6-4・§7 の置き換え案

本修正の後は、Release に `hit_record.csv`・`sent_YYYYMMDD.txt` とそれぞれの `.bak` が作られ・更新される。これは正常な動作であり、現行の §6-4 と S1・S2 では停止条件に当たる。

### 2.1 §6-4（Release への書き込みの範囲）

現行：「`buyscore_log.jsonl` に書き込むことと、その保存に伴う `buyscore_log.jsonl.bak` の更新を認める。それ以外の asset への書き込み、Release の新規作成・更新、メール送信の再開は認めない。」

案：「`buyscore_log.jsonl`・`hit_record.csv`・`sent_YYYYMMDD.txt`（YYYYMMDD は8桁の日付）への書き込みと、それぞれの保存に伴う `.bak` の作成・更新・削除を認める。それ以外の asset への書き込み、Release の新規作成・更新、メール送信の再開は認めない。」

### 2.2 S1（置き換え）

現行：「notify のログに `[hit_record] N件追記` が出る、または Release の `hit_record.csv` が作られる・更新される」

案：次のいずれかが確認されたら停止する。hit_record の正常な生成・更新そのものは停止条件にしない。

| # | 条件 | 確かめ方 |
|---|---|---|
| S1-a 列構造 | Release の `hit_record.csv` のヘッダが notify の44列（notify L5149 からの fieldnames）と一致しない、またはヘッダと列数の違う行がある | Release の `hit_record.csv` を読み、ヘッダと各行の列数を数える |
| S1-b 消失 | `hit_record.csv` の行数が `.bak`（直前の版）より少ない、または `.bak` にあるキー（date, venue_num, race, pred_combo）が `hit_record.csv` に無い | `.bak` と本体のキー集合を比べる |
| S1-c 破損 | `.bak` にある行の内容が、本体で変わっている（同じキーの行は追記しかされない前提のため） | `.bak` の各行が、本体にそのまま含まれるかを比べる |
| S1-d 保存の停止 | notify のログで、hit_record の保存失敗（`[release_storage] hit_record.csv:` で始まる ERROR）が2回の実行で続けて出る | notify の実行ログ |

### 2.3 S2（置き換え）

現行：「Release `data-store` で、`buyscore_log.jsonl`・`buyscore_log.jsonl.bak` 以外の asset が作られる・更新される、または新しい Release が作られる」

案：「Release `data-store` で、次の asset 以外が作られる・更新される、または新しい Release が作られる：`buyscore_log.jsonl`・`hit_record.csv`・`sent_YYYYMMDD.txt` と、それぞれの `.bak`」

注：保存処理は、失敗したアップロードの残骸（state が uploaded 以外の上記の名前の asset）を削除する。削除は上記の名前に限る。

### 2.4 変えないもの

S3（メール送信の痕跡）、S4〜S6、§7 の戻し方は変えない。x_ranking の検証・実績ページ・note のメールは本修正の前から送られており、変わるのは本文の数字だけである（S3 の「メール送信の再開」には当たらないと考えるが、判断はユーザーが行う）。

## 3. 残るリスク（本修正では解消しない）

- 実環境の GitHub では未試験。使う API は今の main と同じ種類（GET・POST・DELETE）で、名前の変更（PATCH）は使わない。
- digest が返らない場合は size だけで検証する。

- 保存に失敗した実行の分は Release に残らない。
- sent ファイルが Release に1日2つ（本体と .bak）ずつ増える（保持期間は未定）。
